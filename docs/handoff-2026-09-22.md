## 1. 先明确交付流程

你的理解基本正确，但服务器验收后通常返回的是“验收回执”，不需要再返回一整套代码。

```text
本机修改代码、启动本地网页、完成必要测试
  → Git 冻结提交 A，生成发布包及 SHA-256
  → SSH 上传到新疆服务器的新候选目录
  → 候选端口验收，失败不动现网
  → 保存恢复点，迁移和切换生产
  → 检查生产健康、版本、数据和 worker，取回验收回执
  → 本机将同一提交 A 及对应发布标签推送 GitHub
```

本机是开发和 GitHub 同步端，服务器是部署、真实模型联调和验收端，GitHub 保存验收后的源码版本。交接记录显示服务器不能稳定直连 GitHub，当前采用离线包与 SSH；本次没有重新测服务器网络。

如果服务器临时修改过代码，先取回独立副本、比较差异、合并为本地新提交 B，再打包验收 B。不能让回执说 A、服务器运行 B、GitHub 保存 C。GitHub 推送失败只记录待同步，不回滚健康的现网。

典型调用：浏览器携带会话与项目 ID → Django 项目中间件及功能权限 → 资源可见性检查 → 业务服务 → SQLite/科研文件。前端隐藏按钮只是展示控制，后端才决定是否允许访问。

计算、智能体、科研工作流有三个独立 worker；网站能打开不代表任务处理进程健康。智能体调用算法仍进入计算中心，不直接执行模型生成的代码。

数据按项目隔离，`owner_only` 进一步限制为上传者和超级管理员可见。公开项目 ID 为 1，允许部分匿名读取；不应按旧设计把所有页面都改回强制先登录。

## 6. 当前电脑的环境问题

师兄原环境是 React/TypeScript/Vite/Ant Design/Mapbox 前端和 Python/Django/GDAL 后端；前端使用 pnpm，后端通过 Pixi 锁定依赖。业务元数据为 SQLite，矢量为 GeoPackage，栅格原始文件和缓存独立存储。

本次只读检查发现：

- Node、pnpm、Miniconda 可找到；Pixi 不在当前命令搜索路径，工作副本未带 `.runtime/tools/pixi.exe`。
- `uboo` 是 Python 3.9.23、Django 4.2.27；项目锁定 Python 3.14，并要求 Django 6。不能直接用现环境跑项目，也不应直接升级破坏其他研究任务。
- `start-local.ps1` 固定调用项目内 Pixi 和 `.pixi/envs/default/python.exe`，依赖未交接的 `config/app.test.toml`。旧本地部署记录中的 D 盘路径、WSL 和 Docker 就绪状态属于师兄电脑。
- 交接快照不带 node_modules、Pixi 环境、本地数据库、模型密钥、计算镜像。恢复源码不等于恢复运行环境。

下一项实际开发准备应是：获准建立兼容的隔离环境后，配置本机独立业务/科研目录、恢复前后端和三个 worker、用 Mock 模型完成最小运行回归。当前不安装新环境，不改 `uboo`，不执行迁移或启动脚本。
