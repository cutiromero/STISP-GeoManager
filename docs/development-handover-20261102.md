## 5. 当前产品要求与不能倒退的体验

- 面向用户的名称为“快速对话”“科研智能体”“逻辑推理”“MH-workflow”。推理强度为轻量、标准、深入；模型选择和高级参数由后台管理。
- MH-Agent 是平台智能助手的产品身份；底层真实模型与权限仍由配置决定。不得把未执行的平台操作写成已完成。
- 智能体输入区保持紧凑，数据、算法、知识选择显式可见，上传文档按钮与其他按钮协调；科研工作流作为输入区入口，过程可折叠，最终文件集中展示。
- 角色按权限由大到小排列；权限核对异常不等于撤权。后端每次仍鉴权，前端不能为了保留界面而绕过真正拒绝。
- 地理工作台侧栏和 MH-workflow 支持调整宽度；工作台侧栏可最小化；加载数据有图例入口，分类栅格应使用实际类别/颜色生成图例。
- 工作台“选择”已改“信息”，“快速加载”改“加载”，专题“编辑版式”改“编辑”。数据洞察随工作台当前数据上下文更新，详细逻辑见下文。
- 首页导航点击与悬停不应推动按钮位置反复弹跳。封面保留后续要求恢复的持续动画背景；这覆盖了此前减动画的部分意见。
- 新闻和简介不展示内部素材来源、课件页码或无意义权限提示；团队/成果用统一蓝色风格。用户界面和数据名称避免“师弟”等准备称谓及装饰性的 `·`。
- 知识网络保持原有协调配色、轻微渐变、点击特效、缩放和清晰连线；不能为了好看伪造知识关系。概览可用领域导航连接，具体依据仍来自条目。
- 成果入口按项目区分：地质修正只在逻辑推理项目，生态评估只在干旱区项目；MH-workflow 场景、工具及数据选项也按项目与输入角色过滤。
- 胡杨群落物种功能性状演示数据只在公开、干旱区生态风险评估分析决策、塔大胡杨三个项目展示。“生态”在历史对话中已确认指塔大胡杨。
- 历史聊天独立于目录数据存在；数据被删除时仍可读聊天，只在访问旧资源时说明资源已删除。

工作台右侧洞察优先跟随点击对象所在图层，其次选中图层，最后左侧选中目录资源；概览通常统计来源资源整体，不是汇总左侧整个目录。接手后若改这块，沿 `MapPage.tsx`、`LayerContext` 和分析上下文核对，让用户能看出当前分析对象。

数据目录已区分原始上传和计算结果，手动计算与智能体计算统一登记真实结果。历史结果删除先预览引用并由用户确认；结束的任务/工作流可以保留名称、来源和删除回执，目录文件真实清理。运行中依赖、尚未结束入库及仍被工程/专题/成果使用的数据继续保护。不要把“用户确认”改成绕过所有依赖检查。

登录使用浏览器会话：正常刷新/多标签交接保留，关闭全部页面后再次打开需登录。当前结合 sessionStorage、30 秒心跳和后端 120 秒访问租约，保留120秒刷新续接；未挂起的页面凭正确令牌可在租约后12小时内恢复。新标签交接失败可join仍在线会话，不能注销其他页面；不能用永久本地Token代替。

项目范围与操作权限分开：角色决定能做什么，项目成员关系决定在哪做。请求每次只用一个项目，API用 `X-Project-Id`、文件URL用 `projectTagId`，冲突应返回400。公开项目通常为ID1；其他项目ID要看各环境，不能把本机ID写死成服务器ID。

数据 `owner_only` 仅上传者与超管可读；知识文档的本人私有空间有自己的严格边界，不因为平台管理员身份就能读。聊天仅owner可读。后台任务执行/恢复时重新检查权限和项目，不能只信创建时快照。旧 `accessGroupIds/audienceGroupIds` 已不承担项目内对象分配。

## 6. 智能体：三种入口与同一任务交互

| 入口 | 实际能力 |
| --- | --- |
| 快速对话 `chat` | 模型对话、澄清问题卡；保持现有权限，不宣称读取平台数据或提交计算 |
| 科研智能体 `agent` | 在当前项目查数据、算法、专家知识；提问、恢复、执行授权计算、读真实输出并解释 |
| MH-workflow | 角色明确、阶段受约束、可持久恢复的科研编排；包含批准、质量检查、报告和地图成果 |

自然语言科研请求可通过 `research_intents.py` 接到持久工作流；显式 MH-workflow 表单保留。它是工具循环与场景编排的结合，还不是对任意科研任务都有效的通用规划系统。

### 问题卡与恢复

普通智能体可由模型调用 `ask_user` 提出单选、多选、文字、审核或算法参数问题，说明缺什么、为什么问、可选项和建议默认值。用户主动提交答案：普通澄清可在卡内确认，也可通过底部输入框回答；审核须在卡内明确选择并确认。默认值不能自动替用户提交。

`AgentRun` 保存请求、模型参数、数据/知识选择、工具返回、执行上下文、问题、答案和结果；`RunEvent` 保存真实事件。流程通常为：

```text
排队 → 处理中 → 等待您回答/等待您审核/等待计算
                   ↓ 用户回答或真实计算结束
               原任务恢复 → 读取结果/继续调用 → 完成
```

等待时释放模型执行资源，刷新或切会话可恢复同一问题。回答校验项目、本人、问题编号、方案修订和提交键；同键同内容复用，旧卡/冲突返回 409。取消等待后有明确终态，不继续发后续操作。

用户给“红光3、近红外8”，影像真实有8波段时直接提取，不因常见传感器排列不同反复质疑；真实只有4波段才指出具体冲突。用户新增条件后要更新计划和真实工具参数，不能只修改回复文案。

### 计算、批准和状态

- 模型提交计算取得真实任务，进入 `waiting_compute`；完成后恢复一次，并通过 `read_compute_output` 读取实际文件/统计，再解释和决定下一步。
- 计算成功、结果入库中、入库完成是三个状态，不能根据模型一句“已完成”替代真实状态。
- 取消智能体任务不自动杀掉已提交计算；真实计算任务卡另有停止能力。暂停在保存点生效，不能承诺中断任意第三方算子内部步骤。
- 地图编辑先形成方案并逐项批准，批准绑定输入/规则/算法/参数/建议摘要和选择范围；实质变化重新批准。通用“同意”不能绕过专用地图批准。
- 工作流保存步骤、执行输入输出、检查点、批准和结果。等待、暂停、失败、取消和完成要在左侧任务栏及对话区一致。

判断摘要和模型思考分开：前者讲“发现、证据、判断、为什么调用、实际结果、下一步”，对应真实工具和引用；后者只保存服务真实返回的 thinking 内容。没有返回时不能编造逐行“内心过程”。

最近并发实现见 `run_concurrency.py`、`views.py`、`interactions.py`、`worker.py` 及迁移 `0018_allow_three_active_runs.py`。个人满额为 409，全局队列上限 30 满为 429；等待恢复也走同一事务锁。实际吞吐仍取决于模型、worker和文件/数据库负载。

扩展交互先读 [agent-task-interactions-20261016.md](agent-task-interactions-20261016.md)，复用现有问题卡、参数卡、恢复和幂等，不再为某个指数单独写固定对白。

## 7. 知识库：已经有 RAG 和 Wiki，但不是完整 GraphRAG

知识库顶栏入口为 `/knowledge-base`；不要与科普 `/knowledge` 混淆。四个知识分区是遥感基础、油气管道、遥感地质填图逻辑推理、干旱区生态安全治理。

### 结构化专家知识

`KnowledgeEntry` 保存主体、关系、客体、陈述、解释、适用范围、前提、例外、别名、来源和可计算规则；`KnowledgeRevision` 保存修订。发布、停用和更新均可追溯。此层检索按关键词、别名和概念排序，本身不是向量库。

知识选择可自动、手选分区、全部或不参考。选择不参考时关闭知识工具并过滤历史知识上下文；选择某分区不能突破项目或个人资料权限。

通用可计算规则当前集中于矿物组合、数值范围和必需字段。综合地质 Demo 的项目试用规则按场景和指定修订开放；草稿不自动进入普通检索。规则正文不是可执行任意代码的入口。

### 文档检索与自动 Wiki

历史正式环境已经部署 WeKnora 文档向量/关键词检索与自动 Wiki，不能沿用早期“尚未部署”的答复。部署采用 WeKnora v0.8.2 的 SQLite 兼容方案、sqlite-vec/FTS5、BGE-M3 1024 维向量；Wiki 使用已配置真实对话模型。

支持 PDF、DOCX、TXT、MD、CSV、JSON；单文档 20MiB、最多 100 万字，保留原件、提取 Markdown 和 SHA，PDF保留页码。扫描件需要先 OCR。同知识空间按原件哈希去重；索引与 Wiki 分别记录状态，失败可重试。

向量、关键词和 Wiki 已有真实历史验收；稀疏向量、ColBERT、Neo4j GraphRAG 未启用。“让知识连成线”展示结构化关系和 Wiki 主题链接，不代表后台已经运行完整知识图谱推理引擎。

项目共享资料与每人私有资料分空间，上游检索带授权白名单，返回后复查。原文、自动 Wiki 和模型解释须区分：Wiki 是整理入口，审核修改仍需原文和明确适用条件。

联合检索目前最多 8 条结构化知识、6 段原文，原文单段 1400 字/总 24KB；全文工具每次最多 8000 字并可分页。这是一次工具上下文预算，不是数据库只有这些内容。做全量统计应走统计/分页工具，不能把前 20 条截断结果当总量。

### 已接入材料的处理原则

- 真实地质材料中筛选相关术语和两篇论文，保留页码/条目定位，区分辞书定义、实测结果、作者解释。PDF作者应引用 Duan 等，不能沿文件名写成 Dai。
- 相同对象、相同条件的矛盾优先本批核验材料，旧内容留修订；不同地区、时代、解释分开保存。同名不同稳定 class 不盲目合并。
- 生态资料复用原干旱区项目及知识分区。K005更新 UNCCD 版本，K006争议数值只归档，重复清单合并；不存在的 K002—K004 不能按编号补造。
- 2026-10-12 文档记有本机项目4的57条地质知识，不代表正式现量；10-16正式交付记有新增6条生态知识、3份审核来源摘要，不能把这些历史新增量当今天总量。
- NDVI变化首先是线索；地下水、降雨、物候、树龄、影像质量等可能影响解释。知识应帮助指出证据缺口与核查方向，而非把下降直接归因为退化。

接新资料的短流程：核版本/作者/争议 → 去重和分区 → 保留出处及适用条件 → 导入并检查索引 → 用科研智能体真实查询 → 核对引用和解释。单看“导入成功”不足以证明模型能正确用它。

细节见 [knowledge-runtime.md](knowledge-runtime.md)、`deploy/knowledge/README.md`、`backend/apps/knowledge/library.py`、`weknora_client.py` 和 `backend/apps/agent/knowledge_tools.py`。本机测试 TOML 默认未开知识集成，与正式启用状态分开。

## 8. 算法：从小包开发到真正发布

算法中心使用 `AlgorithmResource`、不可变 `AlgorithmVersion`、`ComputeTask`、`ComputeAttempt`、`ComputeOutput`、`ComputeImport`。版本包 ZIP 包含 manifest 和代码，声明输入角色、格式/波段/字段、参数、输出、超时及质量报告；协议为 `python-geospatial-v1`。

开发步骤：

1. 先查算法库已有版本，复用已发布 NDVI、NDWI、统计、地质检查/编辑能力；不要每个 Demo 再造同名算法。
2. 新能力从可信的小算法包开始，输入/输出按协议声明；用独立小样例运行，核对数据、参数与实际文件。
3. 注册资源，上传新草稿版本，执行平台真实 trial；失败保留记录，不能只填一个“成功”状态。
4. 验证输出格式、类型、坐标系、统计、校验和和质量条件，冻结实际环境 digest，再发布。缺成功试运行或环境 digest 的版本不能发布。
5. 以正式计算任务运行，固定版本/参数/输入快照；计算成功后再独立执行入库，保留目标资源与任务关系。

编辑源码要升版本。上传代码不直接被 Django import，计算在 worker 的独立执行环境中运行。manifest、输入路径、输出路径和结果登记都由后端核验。

当前本机和 AutoDL 使用 native 执行器，已有 Conda/Python 短生命周期子进程，不等于 Docker 隔离。只向可信维护者开放上传/发布，不能拿当前模式运行任意不可信代码。Docker是保留的另一种后端，今天本机 WSL/Docker不可用，不要照旧 Pixi/WSL部署文档直接执行。

计算中心与智能体参数卡复用 `ComputeAlgorithmFields.tsx`，参数格式、默认值和校验要一致。区分源栅格与显示COG：核波段数/CRS时读取原件，避免把显示alpha波段当科学波段。

## 9. 三类演示：接手后应该能讲什么

### 9.1 干旱区生态风险评估与证据更新

场景：`ecology_investigation`，只在干旱区项目展示。

用户用自然语言发任务，智能体读取前/后期影像及 NDVI、分区、有效掩膜和辅助观测，实际统计变化，检索生态知识，形成调查排序。影像质量不足的区域单列“优先补资料”。新证据更新时绑定同用户/同项目前次成功任务，复用已经核验的变化成果，重新评估排序和解释。

10-10本机最早验收是模拟资料、模拟判断服务配合真实 GIS 计算；后来真实模型/服务器验证另有回执。当前演示也不是已经建立野外因果验证的生态风险预报系统。说明见 [dual-demo-20261010.md](dual-demo-20261010.md)。

### 9.4 如何实际演示和交付文件

有两个操作入口：

- 自然语言入口：切到相应项目，从成果展示选择案例“开始体验”，进入科研智能体并自动提交案例请求，观察模型查资料、检索知识和继续执行。
- 参数表单入口：从MH-workflow选择场景，用“预设”恢复资料或手选；“按名称匹配资料”只匹配唯一候选并提示缺项/重名。点击“生成执行计划”，核对当前输入、参数和版本后执行，改配置后重生成计划。

后续共同过程：

1. 观察真实检查、知识引用和建议；缺信息时在原任务中回答。
2. 审核卡选择批准或拒绝。拒绝保持，批准只改所选。等待时刷新可恢复原任务。
3. 完成后看独立讲解页，按上一处/下一处逐项看“发现、知识、算法”；知识和测量默认折叠。
4. 点“在地理工作台对比”，自动组织改前、改后、修改范围图层组；同视角/比例尺/颜色，橙色高亮，支持同步双图和刷新恢复，重复入口去重。
5. 最终文件区集中预览/下载地图、CSV、Markdown报告并按权限入库。现有MD报告是明确能力，不意味着所有算法自动生成Word。

两个地质结果入口：`/map?geologyReview=<任务UUID>&projectTagId=3`；常规工作台对比：`/map?geologyCompare=<任务UUID>&projectTagId=3`。需先登录并具有项目权限。

MH-workflow中“待检查地质图”和“制图范围”仅接受合格面矢量（GPKG、GeoJSON/JSON或完整Shapefile ZIP）；规则表是CSV/TSV/XLS/XLSX，还要检查几何/字段/CRS/稳定ID，不能只看后缀。制图范围说明哪里应完整覆盖及例外；专家规则是可计算条件，知识库补充来源与适用解释，当前没有任意规则语义冲突的通用判定器。

修改高亮要覆盖几何、类别、代号、状态和权重，不能只做几何差集。“涉及对象面积”与“实际几何改变面积”分别统计。原图/独立参考/评价标签分开存，不把参考答案注册成普通资源。

讲解口语稿：“先让系统读图、查专家知识，找到有依据的疑点。我们选择批准哪些建议，算法只改这些对象。再看复核和前后地图，最后解释调查建议为什么变化。这里每个数量、面积和修改原因都能追溯到本次任务。”

进一步看 [geology-map-review-demo.md](geology-map-review-demo.md)、[geology-complete-demo.md](geology-complete-demo.md)、[geology-multi-evaluation.md](geology-multi-evaluation.md) 和 [2026-10-21-workflow-inputs.md](2026-10-21-workflow-inputs.md)。

### 11.2 如何复用已有发布工具

上一轮工具在 `.runtime/agent-concurrency-access-20261102/release-tools/`：

## 12. 运行维护、备份、性能和通知

### 启停与定位故障

先查内部应用，再查公网转发；内部好、公网坏时重点查映射/网络。应用正常但智能体或计算不动，分别查agent/workflow/compute心跳、任务状态、模型和执行器，不要重启整机解决所有问题。

```bash
# SSH进入后，只读诊断
curl --max-time 5 -fsS http://127.0.0.1:6007/api/health/
ss -ltnp
df -h /root/autodl-tmp
tail -n 100 /root/autodl-tmp/geomanager-release-0.1.51-d3b3e82-r1/production-agent.log
tail -n 100 /root/autodl-tmp/geomanager-release-0.1.51-d3b3e82-r1/production-compute.log
tail -n 100 /root/autodl-tmp/geomanager-release-0.1.51-d3b3e82-r1/production-workflow.log
```

当前发布日志还包括 `production-server.log`，候选为 `candidate-*.log`；常规启动日志可能在业务根同级 `logs/`，以实际进程重定向为准。旧路径日志不更新不一定代表服务没启动。

确认应用角色未运行、现用启动指针正确后，可使用既有 `/root/autodl-tmp/geomanager-start-6007.sh`恢复。该启动器内也有知识/向量ensure，先阅读并核身份，避免重复拉起。`/etc/autodl-geomanager.sh`存在且调用它，但本次没有做整机断电自启测试。

没有验证可通用使用的 `systemctl restart geomanager`，不要凭空照写；禁止 `pkill python` 或批量杀GPU进程。维护只管理本项目核实身份的进程，重启应用不等于重启大模型。

权限问题先记录账号/项目/时间/HTTP状态和脱敏响应。401是登录，明确403是授权，409可能是并发或旧方案，429是队列保护，超时/网络失败不能改说“未获准”。后台任务可能继续，先查真实任务，不能因为页面刷新失败重复提交。

### 备份与恢复

超级管理员入口 `/admin/backup`；后端现有 `run_backup --plan platform|research` 支持按配置执行。平台备份范围包含database、media、uploads、config、projects、exports及可选logs；科研备份为research根。

SQLite用在线backup或受控停写快照，不能只拷贝正在写入的 `meta.db` 而忽略WAL。恢复一起检查资源文件、算法包、任务输出、知识文档、引用和会话。正式数据永远不由本机测试库覆盖。

WeKnora需连同自身SQLite、files、bridge配置、密钥和平台映射同批备份。恢复顺序通常是运行环境/模型→向量1024维→知识19020及文件库→平台数据与四角色→权限、原文和Wiki检索验证。仅有平台meta.db不足以恢复全部RAG。

当前证据中有同盘发布备份，不等于已有独立磁盘、定期完整备份和恢复演练。接手后确认备份目的地、可用空间、最近一份可恢复快照及保留周期。

## 13. 两个人怎样用 GitHub 协同开发

建议保持简单：**一个主仓库、一个主分支、每人一个固定个人开发分支、PR汇合、每次一个发布负责人。** 目前不需要再加develop/release多层长期分支。

### 13.1 先把接手基线弄对

拥有者在私有库邀请接手人的独立GitHub账号，按实际需要给Write权限；维护者权限留给负责合并与发布的人。仓库保护功能随GitHub套餐和权限而异，当前没有代为设置。

新电脑应恢复开发者已有的固定个人分支，当前开发者示例：

```powershell
git clone https://github.com/cutiromero/STISP-GeoManager.git
Set-Location STISP-GeoManager
git fetch origin
git switch codex/xintao
git rev-parse HEAD
```

示例中的 `codex/xintao` 是当前开发者的固定个人分支，其他开发者使用自己的身份分支。新开发者仅在首次建立个人分支时从已核实的最新 main 创建，此后连续任务始终复用。

下一步建议由维护者先比较 `origin/main` 与 `v0.1.51`。若主分支确是祖先，采用快进或保留原提交的合并使其包含当前正式代码，再合并本交接文档；不要对已公开协作的历史强推。若直接使用会压平SHA的squash/rebase，须另清楚保存生产tag与映射，不能声称新SHA和旧回执同一提交。

本次只新建/推送交接文档分支，没有合并main、设置成员权限或改动生产标签。

### 13.2 推荐分工

| 人员/角色 | 主要负责 | 协同接口 |
| --- | --- | --- |
| 前端与交互负责人 | agent、地图、结果讲解、参数卡、UI测试 | 主持OpenAPI和mock需求，先给契约 |
| 后端与算法负责人 | 权限/任务状态、工具、知识接入、算法和worker | 依契约实现、迁移、真实输出与测试 |
| 当次发布负责人 | 基线冻结、候选、正式备份/切换、回执/tag | 任一人可轮值，同一时段仅一个人发布 |

两人都能全栈开发，但每个任务明确文件归属。共享热点 `AgentPage.tsx`、`MapPage.tsx`、`docs/openapi.yaml`、生成类型及数据库迁移一次由一人协调；另一个人负责别的模块或等契约落地，避免同时大改同文件。

每人自己clone、自己本地库和资料根。不要两个人直接在同一个共享工作目录或生产程序目录编辑；需要同机多任务可用独立worktree，并分别配置端口/数据根。

### 13.3 日常最短协作流程

1. 建一个小任务，写清目标、负责人、主要文件、数据/接口影响和验收方式。
2. 复用开发者自己的固定个人分支 `codex/<developer>`，从已整理后的最新 main 同步更新；连续任务不得按功能另开分支。当前开发者使用 `codex/xintao`。
3. 看status/diff，按文件提交；已有别人暂存的内容不一起带走。提交格式如 `fix(agent): preserve waiting question after refresh`。
4. 推自己的固定个人开发分支，开PR，写用户变化、必要验证和数据/迁移注意点。小改互看即可，复杂权限/删除/迁移重点看对应边界。
5. 合并前核对共享契约和迁移冲突，指定本次发布人。需要发版时再冻结同一SHA做候选和正式验收。
6. 发布人记下版本、SHA、回执、备份和验证；另一人更新本机代码与迁移，不从生产下载整个目录覆盖本机。

针对普通任务的提交/推送示例：

```powershell
git status --short
git diff -- <本轮文件>
git add -- <本轮文件>
git diff --cached -- <本轮文件>
git commit --only -m 'fix(agent): improve task interaction' -- <本轮文件>
git push -u origin HEAD
```

用明确文件避免把本机数据、旧暂存脚本或图片一起提交；不要 `git add .`。任何历史全量推送都避免 `push --all`、`--mirror`、`--tags`，原始交接旧历史含明文口令。正式tag只单独推本次已验收标签。

生产数据库仅由一个当前正式实例维护；候选是独立副本。数据和模型放受限共享存储/备份，Git只放版本、哈希、来源及必要小文本。算法包作为不可变版本入平台；专业资料不要通过临时聊天附件作为唯一保存地。

## 14. 用 Codex 接续开发的建议

把代码仓库作为工作目录，开工先读最新 `AGENTS.md` 和本手册，再读相关模块/最近回执。历史长聊天用于找来源，不能覆盖当前代码、运行配置和最新用户要求。不要只交一个早期“开发环境文档”给新助手。

保持以下习惯：

- 一次一个清楚的小目标，说明页面入口、预期行为和必要验收；给截图时同时写出账号/项目/操作步骤。
- 先核对现有功能和真实状态，尽量复用参数卡、问题卡、工具、持久状态及地图对比，不新造平行实现。
- 修改前看status/diff，保留原修改和暂存；一次写入不超过500行，分块编辑。只跟踪代码和必要md/txt。
- 后端执行前点载环境；资料脚本优先uboo，项目后端/GIS用已有stisp-geomanager。未授权不要重建环境或全面升级。
- 并行分任务时按文件/模块分工，OpenAPI和迁移指定一个人协调；每个子任务知道还有别人工作，不回滚别人修改。
- 验证结果区分自动化、真实模型、实际算法、页面和生产；没有做的直说。用户要求上线时做到正式验收和同SHA同步，不停在本机。
- 汇报明确用户在哪个页面看变化、当前本地/服务器是否生效、测试创建的数据/任务怎样保留；不给观众堆复杂ID。
- 普通任务按范围必要检查即可。不要自动重构全站、加多层流程、编论文或为每个按钮建一套测试。
- 知识解释可能出错；要求核原文、适用条件和真实工具证据。地质修改必须走批准，不靠模型自信程度决定写入。
