# 业务流模块排查结果

## 范围与结论

本次覆盖业务流定义、启动、主执行循环、专业逻辑适配、资料衔接、模型协议、独立审核、人工恢复、上下文整理、循环预算及报告导出。

主要问题集中在保护层的错误叠加、机械的自证要求和最终报告遗漏分析正文。必要的工具结构、数据合同、授权和人工审批仍有实际作用，应保留；不应把逐字复述、写作措辞和重复辅助索引升级为科学结果是否有效的判据。

## 已修复问题

| 问题 | 对执行的影响 | 当前处理 |
| --- | --- | --- |
| 同一错误码与补救类别只能使用一次 | 不同参数第二次调整也被拒绝 | 按实际方案摘要识别重复，允许同类不同方案 |
| 节点累计时限取单次请求时限的更小值 | 连续几轮深度思考提前耗尽整个节点 | 节点累计时间和单次请求分别检查，资料衔接同步使用相同规则 |
| 节点默认仅8次模型请求、180秒 | 查询、预检、计算、读取与一次修复就可能接近上限 | 默认32次、3600秒；保留可配置和任务总保护 |
| 调度与结束任务扣到当前节点 | 最后一个节点完成后仍可能卡在结束动作 | 任务控制只计任务额度 |
| 任务预算未预留主执行调度开销 | 32目标的最短路径也可能超过默认64次 | 按目标数加1预留必要调度请求，总上限仍为256次 |
| 用完最后一次补救就拒绝收集结果 | 最后一次修复已经成功仍无法交付 | 已提交的计算先正常收集结果 |
| 提问恢复读取原始节点中不存在的合同 | 使用自动合同的主执行流程无法在回答后继续 | 恢复入口复用主循环的合同编译，不创建新执行者 |
| 节点必须逐字复述验收条件 | 正确结果因表述或顺序不同失败 | 验收依据真实输出、语义、证据和已配置审核；自述可选 |
| 审核通过必须抄写全部证据编号 | 辅助索引遗漏也会导致整体退回 | 覆盖关键证据、实际输出和当前执行结果，其余按实际使用引用 |
| 格式修复机会在整个节点内只给一次 | 前面修复成功后，后续独立格式错误直接等待 | 限制连续错误，有效动作后清除该轮错误状态，计数仍累计 |
| 执行、审核、衔接额外固定32K输入上限 | 管理员和服务允许更大窗口时仍被隐藏上限拒绝 | 使用实际用户策略和服务窗口，不设置角色专属32K上限 |
| 只收紧证据，行动历史可能仍然很长 | 无需补充证据也可能进入窗口等待 | 自动收紧近期行动；专业工具请求先收紧历史，再按需精确去重 |
| 通用投影和分批摘要可能替换关键事实 | 数字、条件、批准范围和实际参数失真 | 保护完整核验事实和执行结论，不交给有损摘要替换 |
| 工具节点强制增加脚本审核 | 流程已选择无额外审核仍无法衔接 | 遵循发布时的reviewScripts配置，隔离执行及真实输出校验继续生效 |
| 新主执行通用计算未强制预检同一方案 | 可能只凭模型自述已预检就提交 | 新主执行模式统一核对相同方案的真实预检摘要 |
| 目录索引本身超观察上限时读取不存在的preview字段 | 可读目录变成运行异常 | 返回有界目录索引、完整证据引用和省略数量 |
| 报告提示只要求简短综述，下载遗漏findings | 报告主体几乎都是固定统计及模板 | 主执行者撰写综合分析；报告包含已接受findings，再附实际统计和处置资料 |
| 报告内部术语的出现本身被视为失败 | 内容有效也消耗返修或中断 | 此类措辞作为写作指导，不作为硬拒绝条件 |

## 仍然需要的协议

| 协议 | 解决的问题 | 保留边界 |
| --- | --- | --- |
| 动作JSON或原生工具调用 | 将模型意图转成明确动作，避免从解释文字猜执行命令 | 一个明确动作及合法参数；允许一次连续格式修复 |
| 算子登记与输入输出合同 | 防止编造版本、错误端口、无效字段与波段 | 实际发布版本、适配参数、真实预检、真实计算 |
| 科学事实及批准范围 | 防止样本冒充全集、未经批准的对象处置和核心算法变更 | 来源、条件、实际统计、校验和、核心算法及人工凭据 |
| 独立审核结构 | 保存具体的通过或退回依据 | 必要节点启用，不能代替用户批准 |
| 控制与状态协议 | 防止重复提交、迟到回调覆盖停止和恢复串用 | 用户、项目、修订、幂等及控制代次 |

这些协议服务于不同的执行边界，不要求模型每轮重复输出全部平台合同。历史节点执行接口仅用于历史发布版本兼容，新业务流进入同一个任务级主执行循环。

## 上下文、token与模型能力

当前没有整条业务流累计输入或输出token总额度。输入token和输出预留属于单次请求保护，任务持续执行由调用次数、算子次数和节点累计时间管理。实际服务窗口不能绕过，单次生成额度还可能被模型思考占用；自动压缩输入不能补回已经被服务截断的输出。

复杂任务优先压缩行动历史、共享台账和重复引用，按需读取成果片段；普通辅助资料最后才采用分批归纳。完整科学事实必须保持，不能为了把请求塞进窗口而删掉不利证据。执行者、必要审核及返修继续继承父运行的思考强度。

对于能力有限的本地模型，明确目标、少量工具、具体诊断、真实默认值和稳定结构通常有帮助。将全部流程写成逐字复述和固定套话会增加协议负担，也不能证明结果正确。推荐由平台负责确定性统计和状态管理，主执行者负责适配、纠错、证据解释和报告；独立审核只放在有明确风险的交付点。

统一搭建和验收标准见 [业务流开发规范](business-flow-development-standard.md)。

## 生效范围

修复属于本地开发版本。远端服务器关闭期间没有上传、切换服务或对正式账号发起新任务。正式站的主执行连续性、完整七节点操作、实际报告分析及下载仍需在服务器恢复后通过可视化网站验收。历史已生成的报告不自动重写。

## 本地验证

- `make verify-fast`：10步通过；789项后端测试和51项检查脚本测试通过。
- `make check-efficiency`：239项后台、32项前端单元及126项本地浏览器测试通过。
- 契约五项、SDK/Mock生成、`build:verify`通过。
- 定向验证覆盖七节点真实算子的科学一致性、主执行跨人工等待、提问恢复、同错误不同方案、最后一次补救结果收集、关键事实保护及报告分析入文。

模型桩和本地浏览器结果用于验证机制与边界，不能替代正式账号、正式模型及正式网站验收。
