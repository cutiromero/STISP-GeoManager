# 逻辑推理智能体执行架构

逻辑推理入口把用户资料、专家知识、模型判断与计算中心连接为可恢复的科研任务。模型提出判断和修改建议，计算中心执行已发布算法，用户批准具体修改范围。工作流状态、批准记录、真实计算输出及其校验和共同决定下一步动作。

持久工作流位于 `backend/apps/agent/`，`geology_multi_element_reasoning` 和 `geology_generic` 使用完整证据分批分析。平台项目与资源边界见 [agent-data-boundary.md](agent-data-boundary.md)，独立评价方法见 [geology-multi-evaluation.md](geology-multi-evaluation.md)。

## 请求与持久任务

浏览器通过 `AgentRun` 处理会话、资料角色和确认交互，`AgentWorkflow` 保存科研执行状态。会话重新打开后从服务端读取已有任务；切换页面、流式连接断开和浏览器退出均不代表工作流重新开始。

```mermaid
flowchart LR
    A[浏览器与 AgentRun] --> B[资料角色与字段确认]
    B --> C[冻结 AgentWorkflow 计划]
    C --> D[模型阶段判断]
    D --> E[计算中心真实任务]
    E --> F[实际检查结果]
    F --> G[完整证据分批判断]
    G --> H[用户批准具体修改]
    H --> I[真实修正与复查]
    I --> J[关系分析、远景分析及报告]
```

各层职责如下。

| 层次 | 主要模块 | 持久对象与职责 |
| --- | --- | --- |
| 会话与任务创建 | `research_intents.py`、`research_actions.py`、`workflow_creation.py` | 绑定真实会话、用户、项目和资料批次；确认角色与字段；创建持久任务 |
| 阶段编排 | `demo_workflow.py`、`workflow_worker.py` | 冻结阶段、算法与输入绑定；占用计算槽；驱动计算、审核、恢复和终态 |
| 请求与响应 | `demo_decisions.py`、`decision_budget.py` | 构造实际证据上下文；计量输入；发送模型请求；校验判断、引用和修改 |
| 完整证据分批 | `demo_decision_batches.py` | 冻结成员范围与签名；顺序请求；保存每批响应和游标；合并已校验建议 |
| 修改审批 | `geology_multi_review.py` | 展开模型建议；保存来源；冻结审核方案；按批准子集生成真实修改表 |
| 计算与成果 | `apps/compute/`、`demo_results.py`、`geology_multi_results.py` | 执行受限算法；读取真实输出；检查质量；按权限入库和读取 |
| 页面投影 | `workflow_projection.py` | 提供轻量状态、分页建议、实际变更对比与检查视图 |

`AgentWorkflowStep` 保存模型请求、模型判断、计算提交、人工审核及成果等步骤；`AgentCheckpoint` 保存可恢复位置。`workflow_worker` 使用独占进程锁，逐次恢复陈旧执行、跟踪计算中心，再领取可运行任务。模型服务和计算 worker 分别承担文本生成与隔离算法计算。

## 阶段与批准边界

完整多要素流程包含 `check → apply → recheck → relations → prospect`，随后执行 `final_analysis`。`lithology` 分段只要求对应检查、修正、复查和最终分析；后续分段按已确认的上游成果建立绑定。

初始计划冻结输入资源修订、算法版本及内容校验和、阶段标识、输入端口绑定和参数。聊天入口中已冻结的算法快照必须完整匹配；缺失快照、扩大阶段范围、替换绑定或变更版本均须重新建立有效计划。传统未提供聊天算法快照的入口仍执行其原有权限与计划校验。

初始确认允许按计划检索、检查与提出建议。`apply` 在提交真实修正前进入 `review_modifications`，用户选择当前方案中的具体建议，服务端核对 `planHash`、方案指纹和全部关联资料后保存批准范围。初始计划批准不能代替逐项修改批准；原方案变化后旧批准不能继续使用。

算子返回 `needs_review` 等质量状态时，工作流保留候选输出并进入结果审核。批准只作用于实际展示的输出，原质量记录继续保留。模型最终分析读取当前批准记录、实际修改表和复查统计，区分已批准范围、实际改变及仍待专业核查的事项。

## 完整证据与分批请求

检查结果中的每个问题行绑定实际输出、原始行位置、规则修订、实测值和输入快照。普通压缩上下文中的代表样本只支持已展示对象，不能用于批准未展示的整组成员。

`geology-multi-apply` 对需要完整覆盖的集合使用顺序批次。每批默认至多 128 个问题行、8 个模型分组，再通过真实 tokenizer 向下调整范围。分组只是相同条件和动作下的结构化表达；模型请求仍包含该批全部成员的必要实测、适用条件、例外与来源定位。

矢量成员与栅格蚀变 `AG-` 单元按相同要素、规则及修订、状态、建议动作、快照、适用条件、例外和知识修订形成确定性的模型展示组。每个 AG 单元本身包含完整的像元聚合测量。展示组不会因为目标岩性、矿物、岩性背景或边界值不同而反复拆分；这些差异仍按成员原值完整展示。目标不一致时，组头使用 `target_code=null`、`targetCodeMode=per_member` 和目标分布，采纳建议时逐成员使用自己的 `target_code`。

`memberCommon` 保存组内完全相同的字段，每个 `sample` 补充该成员的不同值；两者合并后可还原该成员的完整必要内容。`memberSource` 和 `sourceRowIndex` 绑定原输出、校验和与原始行位置。分组和排序只改变展示打包，不能将一名成员的条件、测量或目标套给其他成员。几何坐标保存在原始输出，地图、审批与计算继续使用真实几何。

成员测量以 `measurementCommon`、`measurementColumns` 和成员 `measurements` 数组无损表达。`measurementAbsentColumns` 使用从 0 开始的列索引区分原本缺失与实际 `null`；`measurementAliases` 只复用与成员原字段精确相同的测量值。还原后保留数值类型、嵌套列表、对象和顺序，不对测量取样或舍入。

对于 `alteration-pixels-v1`，模型可省略纯地图定位的 `bbox` 与 `representatives[].bbox`，同时保留全部面积、像元数、组分数、矿物、岩性背景、边界、单元及代表面积。省略路径在请求中明确标记，模型不能声称已核查未展示的坐标；绑定条件、例外或配置明确使用这些坐标时，原值仍完整展示。原始输出和内容指纹不变。

模型对蚀变聚合组须明确输出 `suggested`、`keep`、`review` 或 `reject`，也可逐项输出合法动作。遗漏的聚合组不能由算子建议补齐。`keep`、`review` 和 `reject` 不会被隐式转换为修正。原 `review` 或 `exception` 候选保持人工裁定；动作必须属于原问题行的 `allowed_actions_json`。`unreviewedRasterCount` 记录全量 AG 校验失败数，独立于错误列表最多展示 30 条的裁剪，存在未审 AG 时不能将结果标为完整覆盖。

建议的 `origin=model_reviewed` 表示经模型审阅形成；`origin=operator_held_candidate` 表示算子保留的独立候选。后者显示为人工裁定项，默认不选中，不能计为模型预测。用户显式改变蚀变动作时，服务端验证原行允许范围，并保留模型原判断与用户裁定来源。

## 请求预算与首批规划

工作流创建时从策略冻结 `maxIterations` 到 `AgentWorkflow.max_iterations`。当前同一数值同时限制阶段判断次数和 `plan.actualModelCallCount`。后者只累计工作流阶段、批次及校验重问的真实生成请求；角色识别、字段映射、需求解析和配色等辅助模型请求采用各自路径，不计入这一计数。

`demo_decisions` 的完整成员分批审阅及 raster protocol 初检把输入预算收窄至最多 15000 token，并继续服从更小的管理员策略、字节保护和模型真实窗口。综合推理的复检、关系分析、远景比较与最终报告属于非编辑决策，先使用 level 3 的专用执行证据视图，再按任务有效的 `policy.maxContextTokens` 计量；它们不会以代表样本取代完整统计来适应成员审阅的额度。其他流程及未识别的阶段保持原有预算。单次总生成上限沿用有效策略的 `policy.maxOutputTokens`，思考与正文共同使用这份额度；正文要求简短，额度须同时容纳任务所选深度模式的思考过程。任务绑定的 `deep` 设置与 `reasoningEffort` 直接传给模型；预算投影不改变思考模式、强度或真实请求次数上限。`workflow_roles` 和 `generic_mapping` 直接使用策略提供的输入及生成额度。

后续执行证据视图完整保留已读取的 `statistics`、`changes`、蚀变质量与汇总和远景证据聚合。批准范围按相同要素、规则、动作及矿物、岩性背景、边界等完整维度合计，批准数、总数、面积与像元数先从全部批准方案计算，不用代表对象推算。完整逐对象批准记录由 `proposalHash`、`approvalScopeDigest` 和来源输出绑定；统计视图不重新审阅对象，也不扩大批准范围。相同列的表采用列式表示，缺失列不冒充实测 `null`。批准数、未批准数和实际改变数分别表达；完整质量信息及其输出引用保持可解析，当前阶段是否已提交仍以 `executionState` 为准。

地图渲染头、重复元数据与来源指纹保存在完整阶段审计；模型只接收后续判断所需的事实与输出身份。重复中文条件按 UTF-8 大小建立精确引用，条件、例外、结构化参数和 JSON 类型不变。首次请求、模型修复及已存响应恢复使用同一预算语义；超过 15000 token 的后续阶段历史请求必须证明使用 level 3 及以上投影。当前用户策略、字节保护和真实模型窗口仍是硬限制，必要事实无法容纳时进入预算复核，不发送超限请求。

模型返回 `finish_reason=length` 时按生成未完成处理，保存已接收内容与失败审计，该次真实请求仍计入 `actualModelCallCount`。生成片段不能当作完整响应通过校验，也不能据此形成可执行修改。

完整消息使用模型服务 tokenizer 计数，包含系统指令、结构化证据、知识和必要历史。模型窗口还需容纳生成预留及 256 token 安全余量。输入计量依次尝试有明确语义的预算投影，保留规则谓词、例外及本批完整成员；单个必要证据范围仍无法容纳时，保存输入预算审计，进入 `review_results`，不提交本阶段计算。

预算投影达到 level 3 及以上时使用知识执行视图，精确保留 `conditions`、`exceptions`、`ruleConfig`、`trialBinding` 和草稿状态。展示元数据及来源摘录可省略；已有结构化规则时不再重复发送 `explanation`。完整原始知识保留在审计中，并以内容 SHA-256 绑定。`check` 阶段将明确属于 `P-` 远景分析的规则延后，同时从 `availableEvidence` 排除对应引用；未知规则保留，后续阶段继续按各自上下文使用适用规则。

完整 `apply` 批次在 level 2 及以上使用执行证据视图：完整保留本批问题成员、已读取的全部规则统计、蚀变质量记录及真实质量警告，结构相同的统计行可以无损转换为 `columns` 表达。其余地图和栅格头、重复蚀变汇总仅列输出身份，完整清单由源 SHA-256 绑定，并移出可引用内容集合。其内容没有在本批审阅，不能代替成员测量；完整原始结果继续保存在审计与文件中。算法只显示已冻结的身份、版本、校验和及参数约束，完整端口契约由原审计和指纹保留；本批不能改计算图或参数。输入角色与上游版本完全相同的标识和修订不重复展示。

level 3 及以上进一步省略模型不需要解释的纯审计指纹、重复执行头、自动生成的资料描述与过时阶段引用；保留当前执行状态、最新统计引用、最新判断、成员身份、知识修订和实测证据。完整输入版本、计算契约、来源指纹和原始请求仍在私有阶段审计中逐项校验，省略其文本显示不会改变授权、批准范围或计算输入。

每批存在有效规则绑定时，仅展开该批规则知识，未绑定的背景知识另列延期审计并移出可引用集合。规则条件、例外和配置继续完整保留；证据不足时模型可以请求复核，不能从延期材料推断结论。没有有效规则绑定时保留原知识集合。`editTask.issueRuleKnowledge` 仅展示本批规则，不变更已冻结的原始规则绑定。批次使用专门审阅指令，覆盖证据、动作、例外、来源与批准边界，不再重复其他阶段的执行说明。

初始计划展示任务请求上限和固定阶段的最低请求需求。检查算法尚未返回真实问题行时，批次数未知。真实模型的 `apply` 在第一批生成前调用 `plan_batches`：复用生产请求构造、知识筛选、预算投影及 tokenizer，冻结每批起止位置、范围指纹、请求指纹和实测额度。规划只进行计量，不创建生成请求或消耗 `actualModelCallCount`。执行复核源签名与计划签名，并严格复用这些范围。

每批真实首请求在占用额度和发送前再次核对规划中的请求 SHA-256。上下文、指令或展示内容变化时保存明确的未发送审核记录，不能沿用旧规划静默提交；校验重问使用自己的实际请求记录并继续服从真实调用上限。

首批前的额度检查要求覆盖全部计划批次的首次生成，以及后续未完成阶段的首次生成。完整流程在 `apply` 后至少预留 `recheck`、`relations`、`prospect`、`final_analysis` 四次；`lithology` 分段预留 `recheck`、`final_analysis` 两次。最低额度足够不保证模型响应一次通过；结构、引用或修改校验失败时，最多追加一次带具体错误反馈的请求，并再次计数。

若首次请求的最低需求已经超过剩余额度，或执行过程中真实请求额度用完，工作流保存 `status=failed`、`phase=budget_exhausted`。已有批准、阶段结果、批次游标、完整响应及请求审计均保留。详情说明已用额度、任务上限、最低剩余请求和已完成进度；旧确认返回 409，避免反复确认同一不可完成任务。

此时通过页面“调整后重新发起”缩小资料范围，或由管理员使用已有策略管理提高允许值后创建新任务。原任务额度不会因普通确认、继续或全局策略后来提高而自动增加。纯输入 token 预算审核与真实生成次数耗尽属于不同状态。

## 模型调用边界清单

七节点不等于七次生成。固定科学算子本身不调用模型；`measured_geology_v1`、`rule_geology_v2` 可自动推进实测阶段，旧任务及启用模型规划的任务仍可能经过相应决策边界。返修必须回到同一个真实请求函数，不另造可绕过预算的通道。

| 调用点 | 请求函数与输入 | 随资料规模增长的部分 | 预算、整理及放不下时的行为 |
| --- | --- | --- | --- |
| 聊天需求解析（目录直接启动不经过） | `research_parser.interpret`：用户目标、此前意图、绑定任务、授权场景/候选/参数协议 | 候选数量、用户文字、此前问答 | 共享窗口预算、精确去重；最多一次协议修正。仍超限返回预算澄清问题，不启动计算 |
| 上传角色建议 | `workflow_roles.recognize_roles`：每份文件名称、类型、实际 profile、此前角色 | 文件数、字段与有界 profile | 共享计量与精确去重；失败转规则建议并显示原因，由用户选角色，不当作模型确认 |
| 字段对应建议 | `generic_mapping.model_targets`：真实字段、示例、规范目标、规则样本匹配统计 | 字段数、profile、规则索引 | 共享计量与精确去重；仍超限回原字段确认卡，不自动批准 |
| 可选输入衔接脚本生成/返修 | `script_preparation.prepare` → `input_script_model.generate/request_node_result`：固定桥接算子、真实字段、输入版本、脚本反馈 | 字段、脚本、反馈 | 通用节点四档整理；专业适配器保留必需证据并精确去重，必要内容仍超限进入等待 |
| 可选衔接脚本独立审核 | `script_preparation.prepare` → `business_flow_review.review_node`：实际脚本与相同来源证据 | 脚本和资料说明 | 独立上下文、共享预算；额度或上下文不足等待，不替代人工确认 |
| 综合检查前决策 | `demo_decisions.decide` → `_decide_once`：目标、输入角色、冻结算法、知识、执行状态 | 规则、输入字段、历史 | 逐级确定性投影；必要条件仍超限进入 `review_results`，不提交本阶段算子 |
| 对象处置/分批审阅 | `demo_decision_batches.plan_batches/run_batches` → `_decide_once`：当前批全部必要成员、条件例外、来源行号、实测、完整统计 | 对象数和分组数 | 每批至多128行/8组，真实分词向下调整；单成员仍超限或剩余额度不足进入等待，绝不拿代表样本批准整组 |
| 处置建议独立审核 | `legacy.review_decision` → `review_node/request_node_result`：实际决策、方案摘要、完整分组统计、来源校验和、有界明确样本 | 分组、独特质量记录、候选建议 | 不重复坐标与同任务质量元信息；精确引用去重。仍放不下进入上下文等待，不落入失败 |
| 修正复核前决策 | `decide/_decide_once`：完整初检/处置/复查统计、真实批准范围、质量记录 | 已读取统计、批准统计、规则 | 第3档执行事实视图，完整合计批准数量/面积/像元；必要事实仍超限等待 |
| 构造关系前决策 | 同上，允许动作 `geology-multi-relations` | 构造统计、规则、历史 | 同一预算与事实视图；不提交超限请求 |
| 远景推断前决策 | 同上，允许动作 `geology-multi-prospect` | 远景分期、等级、条件组合及实测分布 | 全量聚合后提供统计，保留质量与知识条件；仍超限等待 |
| 最终分析/报告撰写 | `decide/_decide_once`，允许动作 `finish`；规则路径还使用 `report_payload` | 多阶段统计、知识及批准范围 | 完整执行/报告事实视图、共享计量；模型正文不是原始明细的替身。必要内容仍放不下等待 |
| 最终报告独立审核 | `legacy.review_decision` → `report_review.report_review_packet` → `review_node` | 报告事实、完整且不同的质量检查、知识 | 与报告生成共用事实投影；保留实际动作数、复查剩余、分期/等级/面积及原批准范围；精确去重后仍超限等待 |
| 独立审核返修 | `legacy.review_decision` 的 `producer` 回到 `decide`；规则方案首次审核走 `review_rule_proposal` | 实际审核问题、返修要求、重做批次 | 仍执行原阶段完整预算与次数门禁，不能重新套用原自动批准。返修用尽是模型协议/审核失败，不伪装成预算问题 |
| JSON/引用/动作协议修正 | `_decide_once`、`model_targets`、`recognize_roles`、`interpret` 各自有界重问 | 上次响应和具体校验错误 | 所有重问重新计量，反馈降冗不削减必要事实；已发送请求计数不回退 |
| 可选成果配色 | `result_colors.model_colors`：真实类别、色表候选、配色修复反馈 | 类别及候选色 | 原有字节/真实分词/窗口门禁及确定性投影；超限使用平台色表，不阻断科学流程 |
| 会话标题 | `conversation_titles._generate_conversation_title`：至多600字符目标、3个名称、64 token生成 | 输入已固定有界 | 发送前仍检查实际窗口与分词；失败保留已有标题，不影响任务状态 |
| 报告预览/下载 | `workflow_reports.generate_report/render_report` | 实际表格与报告文本 | 确定性生成，不存在额外的模型撰写请求；预览和下载分别校验当前授权 |

### 统一预算、档位与等待

`business_flow_context.input_budget` 是输入额度的唯一计算入口，取当前策略输入上限与实际窗口扣除本次输出额度及256 token安全余量的较小值。字节限制同时生效，不提高服务窗口或管理上限。`TokenMeasurements` 在一次准备中缓存完全相同的消息计量；缓存只复用分词结果，不复用权限、模型响应或科学判断。

公开 `contextManagement.level` 始终是四档：0为基础执行视图，1为去冗整理，2为有明确范围的索引/统计视图，3为完整成员分批或后续执行事实视图。通用材料允许明确标记的有界摘要；专业流程的条件、例外、质量、实测统计与人工批准范围不交给自由摘要截断。专业 `project_payload` 历史0至4的编号作为私有投影配方保留以复验旧请求指纹，其中3、4均属于公开第3档，不再构成另一套预算或等待规则。`projectionRecipe` 解释具体编码，`contextManagement` 解释统一档位与实际限制。

后续决策只合并完全相同统计维度，完整计数、批准数、面积和像元数从全量方案求和；不裁掉规则条件，不以样本代替分组事实。专业独立审核只做事实投影和精确引用去重，无法在安全预算内提供必要事实时直接等待，不进入会丢掉科学内容的通用自由摘要。

专业台账由 `ledger.professional_ledger` 从已完成阶段建立，只保存简短结论、真实任务/输出身份和实际批准标志；它是历史索引，不是新的证据或批准。审核者不能据台账声称看过未发送的逐对象内容。

预算等待保留已有任务、批次、请求计数与批准记录，工作流为 `waiting_approval`，对应业务节点显示 `waiting_context`。专业 `retry_context` 沿用节点决定通道，核对当前项目、任务所有者、节点、revision和幂等键；不能跳过必需科学证据、重置模型计数或写入 `human.approved`。用户调整实际输入预算后可重试；冻结请求额度已不足的任务保留等待记录，须收紧任务范围后重新发起，不靠重复点击恢复额度。原专业结果确认卡的预算重试同样不批准任何输出。

失败及预算等待通过既有 `AgentWorkflowStep` 记录 `workflow_diagnostic`，`action.diagnostic` 包含 `category`、`reason`、`nextAction`、`nodeId`、`recoverable`，`error_code` 为预算、模型协议、算子、数据、权限、超时对应的稳定英文分类。现有详情和时间线显示中文类别及下一步，不增加接口字段或新事件通道。

### 预算回归门禁

`test_logic_flow_budget_audit.py` 使用上传用资料的真实对象、字段和类别规模，构造保持协议结构的合成问题，按1、5、20倍扩展对象、问题和分组；规则身份不随对象复制而伪造新知识。桩分词器每个汉字计1 token，其余每3字符向上取整，并为每条消息加16 token。模型窗口分别为32768、16384，生成预留4096；每个实际发出的请求断言不超过自身预算。测试覆盖非法JSON重问和最终审核返修；`test_business_flow_legacy.py` 强制必要请求无法容纳，验证零生成与上下文等待。`test_logic_auxiliary_budget_audit.py` 在同一六组配置下通过真实入口覆盖角色、字段、科研解析和标题。逐请求JSON与汇总表保存在 `.runtime/task-h/budget-audit/`。

`test_logic_upload_e2e.py` 则使用上传用七份原始文件、真实工作副本、真实本机科学算子、正常确认接口和Mock审核，验证七节点与报告预览/下载。其规则为仓库合成试用夹具，结果只证明业务连通，不代表真实地区的科研精度。测试使用隔离数据库，生成资料保留于 `GeoManagerData-logic-qa` 的独立任务目录，记录与报告保留于 `.runtime/task-h/local-e2e/`。

## 响应持久化与恢复

真实请求发送前先保存 `requesting` 审计并占用一次请求额度；返回完整响应后先保存 `response_received`，再进行 JSON、引用和动作校验。通过校验才保存该批判断、建议和完成游标。请求记录包括请求内容指纹、输入 token、字节数、生成额度、实际 usage、响应存档及校验状态。

| 已保存状态 | 恢复行为 |
| --- | --- |
| 已完成批次与连续游标 | 核对真实源范围和已保存响应，复验判断并合并建议，不再请求生成 |
| `response_received` 且完整响应存在 | 读取已保存响应并完成校验，不重新发送同一请求 |
| 明确 `requested=False` 的额度阻断 | 不认定为已发送请求；保留阻断审计 |
| 已发送但完整响应未保存 | 停止并保留审计，避免把未知请求静默重发 |
| 原响应已被拒绝、修正请求未能发送 | 保留原拒绝及额度阻断，要求重新发起，不静默再问 |
| 源数据、规则、版本、预算签名或批次范围变化 | 拒绝沿旧游标继续，保留原记录 |

阶段判断次数只在新阶段占位一次，恢复已有真实批次不会再次占位。纯输入预算审核或尚未发送的预规划因暂停、取消、撤权而停止时，释放未使用的阶段占位。旧记录缺少发送标志时按保守口径处理，避免未知进度被当作从未执行。

已提交算子由真实 `ComputeTask` 引用跟踪。worker 恢复 `waiting_compute` 时观察该任务状态，继续读取输出，不从头提交同一算子。陈旧 `running` 恢复使用已保存计划，阶段中的真实任务引用优先于新决策。

每次 worker 推进最多新增完成一个审阅批次。原始响应、校验后的动作、完成游标和覆盖成员数持久化后，剩余批次重新排队；下一次推进使用原策略的单步时限，复验已完成批次而不重复生成或增加阶段次数。暂停、取消和撤权在重新排队前再次核对。修正回复发送前也须预留其余已规划批次及后续阶段的最低请求额度。

分组回复保留 `group_id`、`disposition`、`excluded_issue_ids`、`reason` 四个必需字段。模型额外重复的 `action`、`target_code`、`weight` 只有在与每个纳入成员的确定性处置完全一致时才可规范化；未知字段、动作冲突、不同成员目标的错误概括及无效数值仍被拒绝。待裁定分组不产生修改，拒绝候选不能携带动作字段，原始模型响应始终保留。

## 暂停、取消与授权

用户控制状态独立于模型计划持久化，旧 worker 保存不能覆盖新到达的暂停或取消。`ModelStreamGuard` 在流式消费、watchdog 和执行边界核对时限、暂停、取消、当前用户权限、输入绑定、知识修订及算法授权；完整证据预规划也使用同一 guard。

一次实际授权轮询可临时复用内部来源索引，嵌套调用共享该轮索引并在最外层退出时释放。下一次轮询重新建立索引，不跨轮询缓存 ACL、资源状态或业务判断。

运行中的取消请求由在途 worker 收敛。worker 停机后，带取消标记的排队任务和心跳过期的运行任务进入已有取消路径：多阶段任务按真实 `submit_operator` 引用核对并取消仍活动的计算，普通工作流已有计算则交 `waiting_compute` 跟踪处理。新鲜运行任务继续由原 worker 负责。终态后释放计算槽，后续新任务可正常排队。

暂停保留已经提交的计算，恢复时接着观察实际结果。取消停止后续生成、提交及入库；已有输出和批准记录仍可在历史授权有效时追溯。

## 数据与审计边界

普通发现只使用当前单一项目中通过 ACL、功能权限、资源状态和准备状态检查的业务资料。任务上传、冻结规则、规范化副本、检查清单及其他内部材料通过真实任务绑定使用，不能因编号已知或出现在旧消息中进入无关任务。

模型上下文不包含评价真值或参考答案。独立评价在预测成果及其指纹冻结后读取专用评价材料，评分过程不向模型或算子回灌答案。演示规则、人工构造数据和专业适用性限制应在结果中明确标注。

通用上传的字段判断可使用本任务已绑定规则中的名称和代号词表作语义提示。请求只增加各字段展示样本的精确匹配计数，不发送完整词表；资料、规则、知识绑定及已确认单元覆盖的权限和版本在生成期间持续核对。统计来自前 1000 行中每字段最多 8 个展示唯一值，每值最多 80 字符；长度达到 80 字符时可能已截断。展示样本命中不能代替全表核验，未命中也不证明没有适用规则。用户提供的单元表在字段确认后可覆盖默认词表，字段映射继续由模型提出并由用户确认。

私有执行数据包括 `modelBatches`、`modelAttempts`、`modelRequestPayload`、请求指令、历史预算审计和完整建议列表。普通 `full`、`card`、`compare`、`inspection` 视图使用受控投影或分页，不把这些私有对象整棵返回。公开模型活动展示实际阶段、状态、已接收计数及受限内容；它不能作为算子完成、人工批准或工作流完成的依据。

地图对比以成功计算的实际变更输出、批准编辑表和输出校验和交叉确定真实改变。候选建议的数量、颜色或模型描述不能代替实际修改记录。
