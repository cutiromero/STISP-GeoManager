# 开发阶段数据与存储规则

本平台当前采用开发环境存储策略。数据的重要性由来源决定，不由目录大小、文件扩展名或测试项目名称决定。

## 数据分类

| 类别 | 内容 | 保留方式 |
| --- | --- | --- |
| 用户原始输入 | 用户上传或直接传到服务器的影像、矢量、表格、原始数据包、文档、附件，以及无法从代码重新生成的输入 | 不删除；原件去重后保留一份主数据和一份独立备份 |
| 原始输入的必要元信息 | 资源 ID、名称、项目、来源、权限、字段含义、原始表内容、CRS、波段和源文件清单 | 与原件对应保存，清理前后校验 |
| 现用访问表示 | 当前原始图层使用的 GeoPackage/SQLite 表、COG、必要索引及现用页面静态文件 | 仅保留现用一份；可重建的表示不额外备份，不保留废弃版本 |
| 测试计算成果 | 算法结果、工作流工作副本、派生数据、计算导出、预览、临时报告和嵌入执行快照的要素/像元副本 | 可删除；验收结束后清理，不进入原件备份 |
| 程序历史 | 历次代码、前端源码、开发工具和构建素材 | GitHub 精确提交管理；服务器不长期保留多套部署目录 |
| 必要运行环境 | 当前 Python 环境、模型服务、现用服务二进制及许可证 | 保留正在使用的一套；不用测试环境或候选环境重复备份 |

运行依赖不能只按目录名判断。当前 WeKnora 的 Jieba 词典位于 `modules/github.com/yanyiwu/gojieba@v1.4.7/deps/cppjieba/dict`，属于运行所需文件，清理 Go 编译依赖时仍须保留。裁剪过运行目录的服务要做正常重启及健康验收，未改动的共享模型保持运行。

目录名称中的 `original` 不保证文件来自用户，目录名称中的 `test` 也不保证文件可以删除。确认原件至少结合上传记录、`is_compute_result`、计算入库关系、源数据清单和 SHA-256；来源无法确认的文件先归档，不直接删除。

原始表格可能已经导入统一 SQLite/GeoPackage，不能只保存散落文件而遗漏表内数据。清理派生表时必须验证所有原始表的行数和内容摘要未变化。多个资源共用一个原件、同一数据表或同一栅格源时，不删除仍被原始资源使用的存储。

## 服务器目录边界

- 当前平台根：`/mnt/data1/stisp`。
- 业务及科研数据：`geomanager-data-20260919/app` 与 `geomanager-data-20260919/research`。
- 旧工作区中独有原件的去重归档：`geomanager-original-data`；其清单将原路径映射到原件或内容寻址对象。已有正式原件不再复制一份到该目录。
- 唯一原件备份：`/root/autodl-tmp/stisp-original-backup`，包含去重原件、只保留原始表的数据库文件、原始资源清单及必要配置；不包含计算结果和候选工作区。
- 共享模型服务：`/root/autodl-tmp/users`，按独立服务维护，不混入平台开发工作区清理。

归档和备份使用 SHA-256 去重。原件至少核对主数据与备份的字节摘要。既有原盘副本可为原件备份提供同盘硬链接，旧副本退场后，原件备份仍持有文件；主数据和备份位于不同物理盘。

## 开发、测试与成果清理

1. 开发前记录所用 Git 提交、原件清单、参数、必要的随机种子和测试范围。
2. 原件先进入主数据和单份备份，再只读使用，不能把会被清理的验证目录作为唯一原件位置。算法确需修改时，创建受控工作副本。普通单元测试使用临时小样本，禁止复制整个正式平台或完整科研目录。
3. 测试在独立临时目录内执行。生成的目录资源必须标记为计算结果，禁止为了省事把输出伪装成用户上传数据。
4. 验收后删除本轮测试输出、工作副本、导出、候选副本、临时包和无用缓存。保留精简的结论、参数、源提交及校验摘要即可；不要在每个节点的计划和事件中反复嵌入完整数据。
5. 已保存的地图、工程、成果展示和历史任务应解除对已删除计算数据的引用，或保留明确的删除凭据；不能只删磁盘文件，留下仍被当成可用数据的目录记录。
6. 原始资源 ID、用户目标和输入参数保持可追溯。需要批量清理时，先停 web、排空任务并停 worker，再使用受控清理实现；原始资源与原始表校验不一致时立即停止后续清理。
7. `apps.core.development_storage.clean_generated_data` 提供原始表保护、共享原件保护、计算记录脱钩和工作流执行快照压缩。它是维护实现，不是公开 API，也不能在正常接收任务时直接调用。

`compute.retention_days` 管理临时输出和部分缓存的保留时间，不能替代已入库测试成果或持久化工作流的验收后清理。开发环境建议临时输出使用 1 天；仍被执行任务引用的内容必须等任务结束后处理。

## 发布时只保留现用代码

发布配置必须启用：

```toml
[server]
developmentMode = true
```

正式应用配置标记当前环境：

```toml
[application.development]
enabled = true

[compute]
retention_days = 1

[backup.plans.platform]
enabled = false
retention_count = 1

[backup.plans.research]
enabled = false
retention_count = 1
```

当应用已标记为开发环境时，标准工具拒绝使用未启用开发模式的发布配置，避免旧配置重新生成全量备份。

开发模式仍执行双锁、提交和进程身份核验、任务排空、数据库迁移分类、结构指纹、兼容性、worker 心跳和 HTTP/静态资源验收。发布过程中只暂存启动器及配置，保留当前旧代码和旧静态树用于失败恢复；不复制整库或完整静态目录，不保存在线/静止数据库双副本。

验收成功后，工具删除上一程序目录、上一静态树、候选中的业务/科研/代码副本及上传压缩包。仅当前程序继续运行。近期保留至多 10 份轻量操作回执，较早操作压缩为提交号、状态和时间等摘要。清理遇到运行进程、符号链接或越界路径时保留该目录并记录原因，不影响已经验收的网站状态。

候选目录无论通过还是失败，在其进程确认结束后清理可重算内容。保留诊断记录，不长期保留整套候选数据库、科研数据和代码。

发布结束检查 `development-retention.json`、`development-cleanup-pending.json` 和 `candidate-cleanup-pending.json`；存在未清理项时必须处理并记录，不能把网站验收通过当作空间清理也已完成。

## 代码恢复与数据恢复分开

历史代码由 GitHub 指定提交恢复。构建图片、依赖锁文件及构建脚本需要一起进入 Git；账号、密钥、用户原件、业务数据库、环境和日志不进入 Git。

恢复历史行为时，在固定个人分支 `codex/xintao` 上形成恢复提交，保留当前数据库迁移记录，按当前结构适配旧代码，再进行候选验证和标准发布。服务器不能访问 GitHub 时，由本机取得源码、重建冻结发布包并上传。

开发模式不提供依赖旧服务器目录的 `rollback`。不通过覆盖旧数据库、逆迁移或忽略结构校验恢复代码；需要找回误删原件时从唯一原件备份按清单恢复。发布失败时的短暂自动代码恢复，与长期保存多套历史版本是两件事。

## 备份约束

原件备份只有一套，按内容去重并维护来源清单。原始表备份只包含保留的原始表及必要的 GeoPackage/SQLite 元信息，不把同一库中的计算表一并长期保存。配置和原件元信息只保留当前可恢复的一份。

开发环境默认关闭整平台、整科研目录的周期性全量备份。测试成果、缓存、执行快照、导出和候选目录不备份。不能用“以后可能回退”为理由，为每次发布再复制一次数据库或科研目录。

迁移前原盘副本是已存在的过渡恢复点，本次保持完整；它不属于后续开发常规备份策略。退出该恢复窗口时单独处理，不在后续开发中继续生成同类全量副本。

每轮清理记录清理范围、源提交或脚本摘要、原件保护清单、原始表校验、释放空间和网站验收结果。记录保留于受控运维目录，不将用户数据和私密回执上传 Git。
